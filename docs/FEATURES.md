# Features, and where they live

One entry per feature: the rule it keeps and the files that keep it. The
package map is in [ARCHITECTURE.md](ARCHITECTURE.md); deeper contracts have
their own docs ([MEMORY.md](MEMORY.md), [ROUTINES.md](ROUTINES.md),
[SKILLS.md](SKILLS.md), [BOT-FILES.md](BOT-FILES.md), [LIVE.md](LIVE.md),
[SECURITY.md](SECURITY.md)).

- **Each profile is its own entity.** One runtime, many bots: persona, memory, artifacts, vault scope, tool allowlist and audit are per profile (the conversation→profile index scopes them). A fresh install has no profiles; the first one created becomes the main bot. Never describe the platform as "one entity".
- **Redirect now** — `packages/mind/src/converse/redirect.ts` + the busy send menu in `apps/web` (`send-button.tsx`, `lib/send-mode.ts`). Steer (default) waits for the next tool boundary; Redirect stops the turn at the nearest safe point (abort streaming; let a running tool round finish within 15 s; deny a waiting approval) and answers the new message. Queued messages stay queued; a cut reply is marked interrupted.
- **Stop propagation (a Stop travels the work tree)** — `packages/mind/src/tasks/tree.ts` (`mind.tasks.stopTree` / `stopChatWork`). The task pill's Stop and a chat's Stop cancel more than the row: the task first (abort its turn, mark cancelled — the root goes BEFORE anything downstream, so a still-running turn cannot react to NACKs by respawning the work), then every pending mailbox message its conversation SENT settles `cancelled` with `senderNotified` set (delivery.ts `cancelSentFrom`: the stopped conversation is never woken — a NACK there would start a turn on cancelled work; an undelivered input is withdrawn from the recipient; one already being answered runs out and signals nothing), and its background bash jobs are KILLED: `ShellBackend.exec` takes an optional `AbortSignal` (local/host kill the child; the VM races the exec and `pkill -U <bot>` clears the bot's processes there — a root home has no per-bot boundary and keeps the 30-min cap), each job rides `JobKiller` (ext `bash-jobs.ts`; the entity wires one instance into both the bash plugin and the task wiring), and a killed job clears its record through `BashJobHost.stopped` with NO wake. Mail sent from a MAIN chat is never settled (the chat lives on); a chat Stop is quiet (no task wakes). REST `POST /api/tasks/:id/cancel` returns `{ cancelled, tasks, messages, jobs }`; the session's interrupt returns the same counts. Tests: `tasks/tree.test.ts`, `plugins/bash-jobs.test.ts`.
- **The global pause (one switch to freeze the crew)** — Settings › Pause the crew + a resumable banner on Now (`components/pause-section.tsx`, `routes/now.tsx`; `ultiv.settings` v4 `paused`, REST `GET/PUT /api/settings/pause`). While on: no task STARTS (spawns queue, the pump holds, resuming refills), cron fires settle `held` receipts without waking anyone, webhook payloads are acked then held, and sensor passes are skipped whole. Chats and approvals keep working. Pause holds like downtime, it does not queue: nothing held replays. Details: docs/ROUTINES.md. Tests: `apps/server/src/pause.test.ts`, `tasks/queue.test.ts`.
- **The daily spend ledger and per-bot token budget** — `packages/mind/src/usage/usage.ts` (`mind.usage`, the `ultiv.usage` doc): every settled turn's tokens (chats, tasks, routines, evals — one sink in `converse.ts` `settleOf`, late-bound through the entity once the profile index exists) sum per profile per day, 30 days kept, the server's local midnight draws the line. `policies.dailyTokenBudget` (Edit bot › Daily budget, `POLICY_NUMBER_FIELDS` bounds, REST `GET /api/usage?profile=` reads it back with today's spend) gates TASK admission: at the budget new spawns are REFUSED with a sentence the model relays to the owner (queue.ts `budgetMessage`), queued tasks wait for the next day, chats with the owner always run. The budget bounds autonomous work, not conversation. Tests: `usage/usage.test.ts`, `tasks/queue.test.ts`.
- **The fallback model (a failed task retries once elsewhere)** — Settings › Fallback model (`components/workspace-fallback.tsx`; `ultiv.settings` v5 `fallbackModel`, REST `GET/PUT /api/settings/fallback-model`, catalog-validated on save). When a task RUN fails and a fallback is set, `tasks/run.ts` switches the task's conversation to the fallback and runs ONE rescue attempt with a `[fallback]` note that warns to check what already reached outside before repeating it; the conversation's own model is restored afterwards, and a rescue that fails again stands (the row carries the ORIGINAL failure). Chats with the owner never fall over silently — the owner is watching those. This is the overnight story: the default model's provider dying at 3am no longer parks every run. Test: `tasks/queue.test.ts` ("a failed run retries once…").
- **The owner speaks in a bot talk** — `mailbox.ownerSay` + REST `POST /api/rooms/:id/say {text, to}` + the composer under a room (`room-timeline.tsx`, no longer read-only). The line joins the room's transcript under the owner's seat (`OWNER_ID "owner"`, shown "You") and wakes ONLY the addressed bot, at its endpoint conversation for the room, framed `[owner] in the bot talk "<topic>"` — the prefix the memory guard (`memory/guard.ts` `originOfPrefix`) reads as the OWNER's voice, so what the owner says in a talk keeps owner authority; the wake also tells the bot where to answer (its main chat, which the owner reads; the message tool when the other bot should hear it). No delivery engine, no NACKs: the owner is present. Test: `mailbox/owner-say.test.ts`.
- **Typed tables per bot** — `packages/mind/src/tables/` (`mind.tables`, the `ultiv.tables` doc): the typed half of the KV plane, for ledgers and trackers that outgrow an 8 KB state value. The `table` tool (ONE tool, one op per call: create / list / rows / add / update / remove_row / remove; chat-safe by the state rule — own data, ungated, rows carry ids like memory handles) writes typed rows (string/number/boolean columns, checked on write with sentences); ≤ `TABLE_LIMIT` 10 tables per profile, rows cap at `TABLE_ROW_CAP` 1000 and prune OLDEST-first. The owner reads them as grids on Crew › bot › Tables (`components/tables-tab.tsx`; REST `GET /api/tables?profile=`, `DELETE /api/tables/:id`). Tests: `tables/tables.test.ts`.
- **Interactive browser sessions in the VM: one broker, one session per bot** — `packages/ext/src/plugins/browser-session.ts` (the facility) + `browser-session-tool.ts` (the `browser_session` tool) over the home VM's BROWSER BROKER (`packages/ext/src/browser/vm/*.py`, installed and talked to by `browser/broker-install.ts` + `browser/broker-client.ts`). ONE chromium per home VM, run by the broker as the VM's `spbrowser` system user over `--remote-debugging-pipe` (NO debug port), the broker's socket in a 0700 folder (`/run/spriessen-browser`): the server reaches it ONLY through the VM's root exec (`ShellBackend.rootExec`/`rootStream`), so a bot's `bash` can reach neither the broker nor the browser. The broker installs itself on first use into `/opt/spriessen-browser/<version>` (the version is a hash of the modules: a fixed broker restarts; `flock` keeps two first calls from starting two) and retires the pre-broker chromium on port 9222. Each bot (keyed by its Linux user; a per-bot VM is `default`; a shared home with no per-bot users is refused) gets ONE session: a private browser CONTEXT (its own cookies — no other bot's context sees them) with one main tab and the popups it opens (followed, at most 3), HELD by one conversation at a time — any other conversation of that bot gets `busy` naming the holder. At most 4 bots browse at once per home (`--max-sessions`; the next gets `full` until one ends — docs/CAPACITY.md). A VM image without chromium or python3 answers `no-browser`, worded as the owner's rebuild. Ops: `open` (the main tab; popups close) / `read` / `snapshot` (the page's clickable and fillable elements, each tagged with a REF number the bot clicks and types by — `[12] button "Sign in"`) / `shot` are READS; `click` / `type` / `press` / `dialog` (answer an alert/confirm/prompt) / `upload` (one of the bot's own files, by id or name, into the page's waiting file chooser or a file field; ≤ 25 MB, over stdin) are ACTS, gated (`gatedWhen` = `isActOp`) with a card naming the act, element and file. Acts are REAL input events (`Input.dispatchMouseEvent`/`insertText`/`dispatchKeyEvent`); an input that opens a page dialog returns at once and the reply says the page waits on it. An act may name its `site`: the broker refuses it unless the page's real host is that site (the hook for per-site approvals). PASSWORD FIELDS ARE REFUSED to `type`. Downloads the bot's act starts (within 20 s; a page cannot drop files unasked; ≤ 25 MB, ≤ 10 per session) are taken off the broker and saved into the bot's files under `downloads/`, named in the result. Life (`browser/session-life.ts`): a session ends on the holder's `close`, its TASK ENDING (`TaskWiring.onSettled` → `release`), 10 idle minutes (an open takeover keeps it awake; the broker's own backstop closes what a restarted server forgot), the owner's Close, or the browser going away; every end SAVES the cookies of the sites the bot signed in to (a finished takeover, a vault login) — sealed with the vault key in `{vault}/browser-signins/{owner}/{profile}.json` (`browser/signins.ts`; only site names in the clear) together with the user agent they were made under — and the bot's next first `open` restores them before the page loads. Each bot keeps a short browsing history (pages, sign-ins, restores, takeovers, downloads, uploads, closes). A session the server still listed that vanishes (the browser stopped, the VM restarted) is a Needs you row, `browser-lost` (`GET /api/needs-you` `browserLost`, last 24 h, dismissable, opening the bot's Browser tab; `spriessen needs` lists it too). Removing a bot (`rest/bot-purge.ts`) closes its session UNSAVED and deletes its saved sign-ins and history (`life.purge`). `browser_open` (the read-only one-page reader) deliberately stays OUTSIDE the broker: a one-shot chromium per call that exits, not counted against the per-home cap. `browser/active.ts` lists one row per BOT (holder, url, title, popup, open dialog, waiting chooser, when) — the owner's Browsers panel. The home VM's network policy stays the reach gate; session content rides `OUTSIDE_TOOLS` (memory taint). Tests: `browser/broker.test.ts` (the REAL broker through its install/start/call scripts against a local chromium and site: per-bot cookies, busy, popups, dialogs, downloads, chooser uploads, the host-checked login fill), `plugins/browser-session.test.ts` (fake broker: the tool, life and sign-ins), `shell/real-vm-browser.test.ts` (opt-in: two bot users in one VM — broker out of a bot's reach, cookies apart, the cast). Capacity: docs/CAPACITY.md.
- **Owner takeover of a browser session, LIVE and BLOCKING** — `browser/takeover.ts` (the registry; the entity wires the facility's `takeovers` into `MindService.browserTakeovers`) + `browser_session` op `takeover` (a bot's ask: one line on what it needs, ungated — asking is a read) + Browsers (`components/browser-takeover-tab.tsx` `BrowsersPanel`: a work-dock tab on the right for every bot, and Crew › bot › Browser for one; each ask a `takeover-live-card.tsx`; REST `GET /api/browser/takeover`, `GET /:id/cast` (SSE), `POST /:id/cast/act`, `POST /:id/cast/size`, `POST /:id/extend`, `POST /:id/finish`, `DELETE /:id`, owner-scoped through the conversation's profile). The ask BLOCKS: the tool call waits while the owner drives and RETURNS the page as it stands when they Finish — no turn ends, no wake to route (the first design woke the bot through a followUp submission, which a settled task conversation silently dropped: the loop never closed). Every close resolves the wait with its outcome (`finished` with the page, `stepped-away` plainly, `timed-out` at the 30-minute cap (the owner's Extend restarts the window, never past 2 hours from the ask; rows carry their `deadline`) so an abandoned ask pins nothing, `replaced` when a newer ask supersedes); the asking turn's abort (Stop, a killed task) closes it as a step-away, so a dead turn never leaves an ask nobody waits on (`plugins/browser-takeover-call.ts`). Because the call blocks, its audit record lands only when it CLOSES: the registry's own `listen` (opened / closed, the cap and replacements included) drives the `takeovers` + `needs-you` signals and a Web Push to the bot's approvers (`push/events.ts` `takeoverPayload`), and each open ask is a Needs you row (`takeover`, ranked right after approvals; `GET /api/needs-you` `takeovers`; `spriessen needs` lists it too) that opens Browsers. While a takeover is OPEN the bot's own ACTS on that session are REFUSED, `open` included (never queued — the page under the owner's hands never moves); the owner drives the page DIRECTLY: the live cast (`browser/cast.ts` + `browser/cast-events.ts` over the broker's cast, `vm/cast.py`, relayed through the VM's root stream) opens in DRIVE mode (a watch cast on the same session is replaced: two screencasts on one page fight), pins the viewport (1280×800 by default, or the owner's screen — `viewport`, phones get the mobile layout — restored on Finish), streams screencast frames sized to the largest viewer (`size`) as server-sent events (JPEG q60; a repaint, not a video; after an act a screenshot stands in only when the page did not repaint within 350 ms) and turns the owner's taps (double-tap too), pointer down/move/up (drag, selection, sliders), hover, typing, keys, wheel/swipe, back, urls, a page dialog's answer and a file for the page's chooser into REAL `Input.*` events. Frames name the page on show (a popup the page opened is followed, and back when it closes); dialog, chooser and download events are never dropped; a download the page finishes is saved to the bot's files (`saved`). Backpressure: the broker's socket writer keeps only the newest frame, and so does each SSE viewer, so a slow phone gets fresher frames, never a growing delay. A finished takeover marks the page's site signed in (its cookies are saved when the session ends); an ask made before any page is open first opens a blank one, so there is always a session to drive. One cast serves many viewers; the last viewer's departure winds it down after a grace, the stream timeout caps it at 30 min (the client reopens on demand), and the ask's own close (finish, step-away, cap, replacement) stops it too. The `takeovers` live signal (`docs/LIVE.md`) makes asks appear and disappear the moment it happens. Tests: `plugins/browser-session.test.ts` (the blocking round trip and every outcome), `browser/cast.test.ts` (hub over a fake stream: drive/watch, downloads, dialogs), `rest/takeover-cast.test.ts` (routes, scoping, SSE, every act shape, Extend), `browser/broker.test.ts` and `shell/real-vm-browser.test.ts` (the real cast).
- **The driving seat (web)** — `components/takeover-live-card.tsx` + `takeover-toolbar.tsx` + `cast-picture.tsx` + `cast-overlays.tsx` + `takeover-key-catcher.tsx`, `lib/takeover-cast.ts` (the stream: frames, `page`/`dialog`/`chooser`/`saved` events, the viewer's size), `lib/use-cast-input.ts` + `lib/cast-pointer.ts` (gestures) + `lib/cast-keys.ts` (keys). The PHONE KEYBOARD: a tap focuses a hidden text field inside the picture (a phone opens its keyboard only for an editable field, inside the tap) whose input is read back as typing — it always holds one zero-width SENTINEL so a Backspace on an empty-looking field still registers; composed words arrive when committed; a keyboard button brings the keyboard back. - **Credential broker** — `packages/ext/src/broker/` (adapter seam `adapter.ts`, `http-adapter.ts`, `net-guard.ts` SSRF/DNS guard, `redact.ts`, `bindings.ts` store beside the vault, `http-request-tool.ts`) wired by `packages/mind/src/act/broker.ts`. The `http_request` tool spends a sealed secret only within the item's binding (hosts, methods, path prefixes, placement header/bearer/basic/query, bots); https only (localhost http opt-in); auth dropped on cross-host/off-prefix redirects; ≤5 redirects, 256 KB request, 512 KB response, 20 s; responses scrubbed; audited as kind `credential` (never the secret). First use per credential+host raises its own card that "Always allow" never covers (server and UI). Bindings are edited in the Vault ("Allow use"; a login chooses "Signing in, in the bot's browser" or "Web requests"); deleting an item drops its binding. Other adapters (ssh/git/SMTP/DB) implement the same interface later.
- **Browser sign-in with a vault login (`browser_login`)** — `packages/ext/src/broker/browser-login-tool.ts` + `totp.ts`, the broker's `browser` adapter (`CredentialAdapterSchema` `http | browser`; `findCredential(…, "browser")`), offered when the mind wires the bots' browsers (`brokerFor(…, browserSession.fill)`). The bot names a vault LOGIN; after every policy check (visible to the bot and its home, a `browser` binding, allowed bots) the server opens it and the home VM's browser broker fills it into the bot's OWN page — username, password and the current TOTP code (RFC 6238, computed on the server; base32 or an `otpauth://` URI) — finding the fields itself (`vm/ops.py` `LOGIN_JS`). The page's host comes from the BROWSER (never the model), and the broker refuses the fill unless that host is one of the binding's sites AND the one the owner approved (`expect_host`, checked at the moment it types). A login's first use on a host raises its own card (`browser_login (first use of a credential)`, never covered by Always allow); later fills go straight through. It fills, the bot submits; multi-step sign-ins take one call per step; passkeys, phone prompts and CAPTCHAs stay with a takeover. Every fill and refusal is a `credential` audit row (adapter `browser`, host, item — no secret byte); a fill marks the site signed in, so its cookies are saved when the session ends. The secret rides the root stream's stdin, never a command line. Tests: `broker/browser-login-tool.test.ts`, `browser/broker.test.ts` (the real fill and host check).

- **Evals (behaviour tests)** — `packages/mind/src/evals/` (`mind.evals`): `/test` in the CLI chat or the flask under an owner message in the web chat (`SaveAsTest` in `components/branch-buttons.tsx`, `branch.saveTest`; both `POST /api/evals`) on an owner message (`capture.ts`) stores the message, where its chat forks (the entry before it), and the reference (the bot's reply and tools up to the owner's next message) in the `ultiv.evals` doc (`store.ts`, last 20 runs kept). - **Turn deadlines (D4)** — `packages/mind/src/converse/deadlines.ts`, wired in `entity.ts`. Each model request must stream something (text, reasoning or a tool call) within the first-token deadline (default 60 s), and a run ends after the turn deadline (default 15 min). Per bot: `policies.firstTokenDeadlineSec` (10–1800) and `policies.turnDeadlineMin` (1–720), null = default. Bounds and the dialog's labels live once in `@spriessen/contracts` (`DEADLINE_FIELDS`, `deadlineProblem`): `profiles/update.ts` `validatePatch` refuses with the dialog's words ("First reply (seconds) must be a whole number from 10 to 1800. Leave it empty for the default."), and the Edit-bot dialog checks the same before sending and shows the problem under the field. Each request attempt (tool round or durable retry) gets its own first-token window; a retry's backoff sleep and deferred polls are not waits; a pending approval pauses both clocks. Retries underneath: pi-durable retries a retryable model error 3 times (2/4/8 s backoff); the SDK itself is left at 0 retries and its own request timeout, so the deadline is the real bound.
