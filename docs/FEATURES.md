# Features, and where they live

One entry per feature: the rule it keeps and the files that keep it. The
package map is in [ARCHITECTURE.md](ARCHITECTURE.md); deeper contracts have
their own docs ([MEMORY.md](MEMORY.md), [ROUTINES.md](ROUTINES.md),
[SKILLS.md](SKILLS.md), [BOT-FILES.md](BOT-FILES.md), [LIVE.md](LIVE.md),
[SECURITY.md](SECURITY.md)).

- **Each profile is its own entity.** One runtime, many bots: persona, memory, artifacts, vault scope, tool allowlist and audit are per profile (the conversation→profile index scopes them). A fresh install has no profiles; the first one created becomes the main bot. Never describe the platform as "one entity".
- **Redirect now** — `packages/mind/src/converse/redirect.ts` + the busy send menu in `apps/web` (`send-button.tsx`, `lib/send-mode.ts`). Steer (default) waits for the next tool boundary; Redirect stops the turn at the nearest safe point (abort streaming; let a running tool round finish within 15 s; deny a waiting approval) and answers the new message. Queued messages stay queued; a cut reply is marked interrupted.
- **Stop propagation (a Stop travels the work tree)** — `packages/mind/src/tasks/tree.ts` (`mind.tasks.stopTree` / `stopChatWork`). The task pill's Stop and a chat's Stop cancel more than the row: the task first (abort its turn, mark cancelled — the root goes BEFORE anything downstream, so a still-running turn cannot react to NACKs by respawning the work), then every pending mailbox message its conversation SENT settles `cancelled` with `senderNotified` set (delivery.ts `cancelSentFrom`: the stopped conversation is never woken — a NACK there would start a turn on cancelled work; an undelivered input is withdrawn from the recipient; one already being answered runs out and signals nothing), and its background bash jobs are KILLED: `ShellBackend.exec` takes an optional `AbortSignal` (local/host kill the child; the VM races the exec and `pkill -U <bot>` clears the bot's processes there — a root home has no per-bot boundary and keeps the 30-min cap), each job rides `JobKiller` (ext `bash-jobs.ts`; the entity wires one instance into both the bash plugin and the task wiring), and a killed job clears its record through `BashJobHost.stopped` with NO wake. Mail sent from a MAIN chat is never settled (the chat lives on); a chat Stop is quiet (no task wakes). REST `POST /api/tasks/:id/cancel` returns `{ cancelled, tasks, messages, jobs }`; the session's interrupt returns the same counts. Tests: `tasks/tree.test.ts`, `plugins/bash-jobs.test.ts`.
- **The global pause (one switch to freeze the crew)** — Settings › Pause the crew + a resumable banner on Now (`components/pause-section.tsx`, `routes/now.tsx`; `ultiv.settings` v4 `paused`, REST `GET/PUT /api/settings/pause`). While on: no task STARTS (spawns queue, the pump holds, resuming refills), cron fires settle `held` receipts without waking anyone, webhook payloads are acked then held, and sensor passes are skipped whole. Chats and approvals keep working. Pause holds like downtime, it does not queue: nothing held replays. Details: docs/ROUTINES.md. Tests: `apps/server/src/pause.test.ts`, `tasks/queue.test.ts`.
- **The daily spend ledger and per-bot token budget** — `packages/mind/src/usage/usage.ts` (`mind.usage`, the `ultiv.usage` doc): every settled turn's tokens (chats, tasks, routines, evals — one sink in `converse.ts` `settleOf`, late-bound through the entity once the profile index exists) sum per profile per day, 30 days kept, the server's local midnight draws the line. `policies.dailyTokenBudget` (Edit bot › Daily budget, `POLICY_NUMBER_FIELDS` bounds, REST `GET /api/usage?profile=` reads it back with today's spend) gates TASK admission: at the budget new spawns are REFUSED with a sentence the model relays to the owner (queue.ts `budgetMessage`), queued tasks wait for the next day, chats with the owner always run. The budget bounds autonomous work, not conversation. Tests: `usage/usage.test.ts`, `tasks/queue.test.ts`.
- **The fallback model (a failed task retries once elsewhere)** — Settings › Fallback model (`components/workspace-fallback.tsx`; `ultiv.settings` v5 `fallbackModel`, REST `GET/PUT /api/settings/fallback-model`, catalog-validated on save). When a task RUN fails and a fallback is set, `tasks/run.ts` switches the task's conversation to the fallback and runs ONE rescue attempt with a `[fallback]` note that warns to check what already reached outside before repeating it; the conversation's own model is restored afterwards, and a rescue that fails again stands (the row carries the ORIGINAL failure). Chats with the owner never fall over silently — the owner is watching those. This is the overnight story: the default model's provider dying at 3am no longer parks every run. Test: `tasks/queue.test.ts` ("a failed run retries once…").
- **The owner speaks in a bot talk** — `mailbox.ownerSay` + REST `POST /api/rooms/:id/say {text, to}` + the composer under a room (`room-timeline.tsx`, no longer read-only). The line joins the room's transcript under the owner's seat (`OWNER_ID "owner"`, shown "You") and wakes ONLY the addressed bot, at its endpoint conversation for the room, framed `[owner] in the bot talk "<topic>"` — the prefix the memory guard (`memory/guard.ts` `originOfPrefix`) reads as the OWNER's voice, so what the owner says in a talk keeps owner authority; the wake also tells the bot where to answer (its main chat, which the owner reads; the message tool when the other bot should hear it). No delivery engine, no NACKs: the owner is present. Test: `mailbox/owner-say.test.ts`.
- **Typed tables per bot** — `packages/mind/src/tables/` (`mind.tables`, the `ultiv.tables` doc): the typed half of the KV plane, for ledgers and trackers that outgrow an 8 KB state value. The `table` tool (ONE tool, one op per call: create / list / rows / add / update / remove_row / remove; chat-safe by the state rule — own data, ungated, rows carry ids like memory handles) writes typed rows (string/number/boolean columns, checked on write with sentences); ≤ `TABLE_LIMIT` 10 tables per profile, rows cap at `TABLE_ROW_CAP` 1000 and prune OLDEST-first. The owner reads them as grids on Crew › bot › Tables (`components/tables-tab.tsx`; REST `GET /api/tables?profile=`, `DELETE /api/tables/:id`). Tests: `tables/tables.test.ts`.
- **Interactive browser sessions in the VM** — `packages/ext/src/plugins/browser-session.ts` (the `browser_session` tool) over `browser/driver.ts`: ONE detached chromium per home VM (loopback port `9222`, profile under `/tmp/.spriessen-browser` — cookies live for the VM's life and never leave it as model-readable files), driven one command per call by an in-VM python3 CDP driver (stdlib-only websocket, installed idempotently at `/tmp/.spriessen-cdp.py`; chromium runs with a hermetic `HOME`/`XDG_RUNTIME_DIR`/`TMPDIR` under the profile: the bot's TMPDIR is absent on an unprepared VM and chromium aborts at launch without its singleton-socket dir, and the hermetic HOME keeps its dot-dirs out of the workspace). Ops: `open` / `read` / `shot` are READS (ungated, like `browser_open`; a shot saves a screenshot artifact); `click` / `type` / `press` are ACTS, gated with a card naming the act and element (`browserActText`; approval words in `@spriessen/present`), and `open` too is refused while an owner takeover holds the conversation; `close` kills the browser. PASSWORD FIELDS ARE REFUSED (the model must never carry a secret to type it — the broker-typed credential and vault-sealed cookie storage are the follow-up seam; docs/SECURITY.md). The home VM's network policy stays the reach gate; session content rides `OUTSIDE_TOOLS` (memory taint). Tests: `plugins/browser-session.test.ts` (fake driver); the real driver needs chromium (opt-in real-VM suite). Capacity: the browser adds ~410 MiB host RSS per VM while a page runs (docs/CAPACITY.md) — prefer one browser-heavy bot per home.
- **Owner takeover of a browser session, LIVE and BLOCKING** — `browser/takeover.ts` (the registry; the entity wires the facility's `takeovers` into `MindService.browserTakeovers`) + `browser_session` op `takeover` (a bot's ask: one line on what it needs, ungated — asking is a read) + Crew › bot › Browser (`components/browser-takeover-tab.tsx`, each ask a `takeover-live-card.tsx`; REST `GET /api/browser/takeover`, `GET /:id/cast` (SSE), `POST /:id/cast/act`, `POST /:id/act` (legacy selector acts), `POST /:id/finish`, `DELETE /:id`, owner-scoped through the conversation's profile). The ask BLOCKS: the tool call waits while the owner drives and RETURNS the page as it stands when they Finish — no turn ends, no wake to route (the first design woke the bot through a followUp submission, which a settled task conversation silently dropped: the loop never closed). Every close resolves the wait with its outcome (`finished` with the page, `stepped-away` plainly, `timed-out` at the 30-minute cap so an abandoned ask pins nothing, `replaced` when a newer ask supersedes). While a takeover is OPEN the bot's own ACTS on that session are REFUSED, `open` included (never queued — the page under the owner's hands never moves); the owner drives the page DIRECTLY: the live cast (`browser/cast.ts` + the in-VM cast driver `browser/cast-driver.ts`, one long-lived python process over the streaming exec) pins the viewport (1280×800), streams screencast frames as server-sent events (JPEG q55; a repaint, not a video — chromium only sends a frame when the view changes; every act is followed by a forced frame) and turns the owner's taps, typing, keys, wheel and urls into REAL `Input.*` events (the frame's metadata maps its pixels back to page coordinates; Enter and Tab carry their text so defaults fire). One cast serves many viewers; the last viewer's departure winds it down after a grace, the stream timeout caps it at 30 min (the client reopens on demand), and the ask's own close (finish, step-away, cap, replacement) stops it too. The `takeovers` live signal (`docs/LIVE.md`) makes asks appear and disappear the moment it happens. Tests: `plugins/browser-session.test.ts` (the blocking round trip and every outcome), `browser/cast.test.ts` (hub over a fake stream), `rest/takeover-cast.test.ts` (routes, scoping, SSE), `shell/real-vm-cast.test.ts` (opt-in real chromium: taps land by coordinates, typing fills, Enter submits).
- **Credential broker** — `packages/ext/src/broker/` (adapter seam `adapter.ts`, `http-adapter.ts`, `net-guard.ts` SSRF/DNS guard, `redact.ts`, `bindings.ts` store beside the vault, `http-request-tool.ts`) wired by `packages/mind/src/act/broker.ts`. The `http_request` tool spends a sealed secret only within the item's binding (hosts, methods, path prefixes, placement header/bearer/basic/query, bots); https only (localhost http opt-in); auth dropped on cross-host/off-prefix redirects; ≤5 redirects, 256 KB request, 512 KB response, 20 s; responses scrubbed; audited as kind `credential` (never the secret). First use per credential+host raises its own card that "Always allow" never covers (server and UI). Bindings are edited in the Vault ("Allow web use"); deleting an item drops its binding. Other adapters (ssh/git/SMTP/DB) implement the same interface later.
- **Background model (per job)** — tasks and background routines run on the bot's `policies.backgroundModel` (Edit bot › Background model, saved on pick), else `SPRIESSEN_BACKGROUND_MODEL` (+ `SPRIESSEN_BACKGROUND_EFFORT`), else the bot's chat model (`packages/mind/src/tasks/model.ts` `backgroundModelFor`; refs checked against the live catalog, an unknown stored one skipped with a warning). `task_spawn` takes `model`/`effort` for one task; the task's conversation is `configure`d before its first turn and the row carries `model`/`effort`. A cron job with `run: "task"` (the `schedule_set` default for new jobs; older jobs read as chat) runs as a background task (`tasks/background.ts` `spawnBackgroundRoutine`) whose result lands in the main chat as a `ultiv.task-report` NOTE (`converse.note`: a write the model reads with its next turn, no turn starts) — `report: "note"` on the task row.
- **Structured task results** — `task_spawn`'s `result_schema` (a JSON Schema, ≤8000 chars, `tasks/structured.ts`): the brief asks for ONLY matching JSON, the final reply is checked with pi-schema (`compile(schema, { formats, unresolvedRefs: "reject" }).errors`), and a miss gets ONE repair turn in the task's own conversation. The row stores `resultSchema` and `structured` (the value, or null when it never matched; `result` then keeps the raw reply); the parent's wake carries a ```json block or says the format was missed; `task_status` returns `structured`; the task sheet shows it as JSON. `parseJsonReply` (`json-reply.ts`) is shared with `generate`.
- **Branching a chat** — `profiles.branchSession` (`profiles/branch.ts`) over `converse.forkInto` (`converse/fork.ts`, pi-durable `fork`): `edit` forks BEFORE one of the owner's messages (editing the first message starts a fresh chat), `from` forks AFTER a bot reply (a reply that called tools takes its `pi.tool-result` entries along). The new session row carries `branchOf: { sessionId, at }`; the source chat never changes. REST `POST /api/sessions/:id/branch` (`rest/branch.ts`; `edit` also sends the text, ≤ `MAX_EDIT_CHARS`); another owner's chat is a 404. Web: Edit on the owner's bubble (inline editor, "Send in a new chat"; not for messages with attachments) and "Continue from here" in a reply's actions (`components/branch-buttons.tsx`, actions from `lib/branch.tsx`'s provider in `chat.tsx`).
- **Evals (behaviour tests)** — `packages/mind/src/evals/` (`mind.evals`): `/test` in the CLI chat or the flask under an owner message in the web chat (`SaveAsTest` in `components/branch-buttons.tsx`, `branch.saveTest`; both `POST /api/evals`) on an owner message (`capture.ts`) stores the message, where its chat forks (the entry before it), and the reference (the bot's reply and tools up to the owner's next message) in the `ultiv.evals` doc (`store.ts`, last 20 runs kept). A run (`evals.ts`, ≤ `EVAL_RUN_MAX_CASES` 25, sequential, in the background) replays each case (`replay.ts`) in a fork `eval:<run>:<case>` adopted under the bot, on its CURRENT tools and model or the run's model, and grades it (`grade.ts`): expectations (`contains`, `tools`, `notTools`, `rubric` via Jev) then Jev's `yesNo` that the reply is at least as good as the reference (≥ 0.5; without Jev the checks decide). EVERY tool call of a replay is blocked by the replay guard (`guard.ts`, a ToolTask `beforeTool` hook installed before boot's `converse.resume()`; the replay list is durable so a resumed replay stays blocked) — nothing executes, nothing asks for approval. A run cut by a restart reads failed (`recover`). REST `/api/evals` (`rest/evals.ts`), live signal `evals`; web: Crew › bot › Tests (`components/tests-tab.tsx`, `test-case-row.tsx`). Fork conversations stay in storage.
- **Projects (goals over days)** — `packages/mind/src/projects/` (`mind.projects`): the `project` tool (start / update / list / show, by `#handle` = the id's first 8 chars; ungated, it touches only the bot's own projects; installed on the always-on path from `projects/wire.ts`) over one `ultiv.projects` doc (`service.ts`, rules in `rules.ts`: ≤ `PROJECT_LIMITS` 10 open per bot, 20 milestones, 50 log lines). The `open_projects` prompt section lists the bot's active and paused projects, a line each, only when there are some. Check-ins on a date go through the gated `schedule_set`. Work links to a project by `projectId` on the task or cron row (`projects/links.ts`): `task_spawn` and `schedule_set` take a `project` #handle resolved against the bot's OWN OPEN projects (`projectRefOf`, read-only over the doc), a background routine's fire carries its job's link onto its task and every fire leads with `(project #handle)`; the project's work (`projectWork`: newest 10 tasks + its routines) is FOLDED from those rows, never stored on the project, and shows under the `project` tool's `show`. REST `GET /api/projects[?bot=]` (each row with `work`, owner-visible tasks and the owner's bots' routines only), `PATCH /api/projects/:id` (status, done/undone milestone numbers, note — logged `by: "owner"`), `DELETE`; live signal `projects`; web Crew › bot › Work (tab id stays `projects`; `components/projects-tab.tsx`: running tasks, goals with their linked work `project-work.tsx`, routines `work-tab-parts.tsx`) and the Now page's Goals in motion.
- **Chats coordinate, tasks work** — `packages/mind/src/profiles/chat-tools.ts`: every non-task conversation (main, sessions, DM threads, webhook thread chats) is offered ONLY `CHAT_TOOLS` (task, talk, memory, schedules/watches/webhooks, skills library, connector admin, vault metadata, file list/delete, bot/team admin, Jev, checklist, graph) through its stored `modelTools` filter (by name; `agentFor(profile, kind)` adds it for chat kinds, `converse.configure` takes `modelTools`), with a `beforeTool` backstop that refuses anything else in a chat and a `chat_role` prompt line; tasks keep the bot's whole allowlist (codemode included). Existing chats are healed at boot (`entity-chats.ts`, before `converse.resume()`). Eval replays get the chat's tools; routine trials the live fire's (`run: "task"` → task). Why structural: prompting alone does not make a model delegate (DeepSeek's dsh-superagent finding; docs/design/dsh-superagent.md). A new chat-safe tool goes on `CHAT_TOOLS` (the test checks every name is defined); anything that reads or acts on the world does not.
- **Tasks in the web** — no floating pill: the chat's one task list (`lib/use-tasks.ts`, provided to the transcript by `lib/chat-tasks.tsx`) feeds the header chip (`components/tasks-chip.tsx`, beside the approval chip, only while tasks run or wait: "2 running · 1 queued", opens the task list) and the live line under each "Started a task"/"Continued a task" row (`components/live-task.tsx`; the present view carries `task: { id }` from the tool's `details`). Every surface draws a task with the same pieces: `TaskRow`/`TaskLine` (`components/task-row.tsx`), `TaskStatusIcon`, and `taskMeta` (`lib/task-text.ts`: "Running · 3m 05s · Searching the web", "Queued · waits for a free slot"). Settings › Background tasks sets the default limit; Edit bot › Tasks at once (`components/bot-limits.tsx`) the bot's own.
- **Tasks** — queue + limits (`tasks/queue.ts`, `tasks/limits.ts`): a bot runs at most `policies.maxRunningTasks` (1–10, Edit bot), else the workspace default (`PUT /api/settings/tasks`, the `ultiv.settings` doc v3 `maxRunningTasks`), else `SPRIESSEN_MAX_RUNNING_TASKS`, else 3; more wait as status `queued` (input kept in `next`, ≤20 per bot, then refused) and start oldest first as slots free (settle, cancel, remove, a raised limit → `tasks.refill()`); admission runs under one lock (`run.ts` `serial`). `task_message` (`tasks/continue.ts`) steers a running task (`[from parent]`), adds to a queued one, or CONTINUES a settled one (a new run in its own conversation, `runs` counts them, one wake per run — request id `task-wake:<id>:<run>`). The wake lists the files the run wrote (`filesBlockOf`, artifact links the chat passes on; `tasks/wiring.ts`). A task the owner's own message spawned or continued carries `lane: "owner"` and rides the owner model lane (`tasks.laneOf`). `notify_owner` (a task's rare progress line: ≥2 min apart, ≤280 chars).
- **Skills** — the procedure library per bot (`skills/` in the mind; contract in `docs/SKILLS.md`): SKILL.md + reference files under `{SKILLS_DIR}/{owner}/{profile}`, agentskills.io-spec names, versions with one-click revert, and origin stamps (`builtin` from `@spriessen/about`, `self`, `owner` via REST, `url`). Tools: `skill_list/load/file/write/delete/install/propose/evolve`; writes are open and audited, deletes and installs are gated (installs through the broker's SSRF guard; raw SKILL.md URLs or .tar.gz skill folders), and `skill_evolve` runs the improvement loop as a task (history-searched evals, Jev-judged candidates) landing as proposals the owner accepts in the web Skills tab (`/tools?tab=skills`) (edit, add, enable, revert, remove; the prompt section only renders when the bot's allowlist includes `skill_load`).
- **`model: null` means the workspace default, never "no model"** — `configure` (`packages/mind/src/converse/selection.ts`) applies the workspace default new conversations start with (`converseService`'s agent) when a selection carries `model: null`: saving a bot on "Workspace default" re-applies its preference to every chat (`applyAgentPreference` in `apps/server/src/rest/profiles.ts`), and a conversation with its model cleared fails every turn with `no_model`. Explicit models are applied as is. The workspace default is LIVE: `profiles.setWorkspaceDefaultModel` calls `converse.useWorkspaceDefault`, so new chats start on it without a restart, and `PUT /api/settings/model` (`adoptDefault` in `rest/settings.ts`) also gives it to the owner's chats that have no model at all (made before any default existed); a chat with its own model keeps it. Tests: `converse/selection.test.ts`, `apps/server/src/rest/settings.test.ts`.
- **The chat's error banner is a sentence, not a tag** — `lastError` comes from `ownerErrorText` (`packages/core/src/error-text.ts`; a failed task's `error` uses it too, so Needs you never shows the bare tag): it reads only known fields (`reason`, `what`, `why`, `op`, an inner `cause` message, the engine's unanswered reasons), scrubs secret-looking values (`token=`, `Authorization:`, bearer and key-shaped strings) and falls back to "Something went wrong (op)". The full error stays in the server log. Test: `packages/core/src/error-text.test.ts`.
- **After a failed run, the queue waits (D3)** — rule: queued messages are never auto-sent after a failed or cut-off run; only the owner's Retry (or a new message) sends them. pi-durable's `afterFailedRun` stays at its default `"keep"`. `retryQueued` in `packages/mind/src/converse/control.ts` writes an empty-model `ultiv.queue-retry` entry, which places the kept inbox in a new run (the model sees nothing extra; the transcript shows nothing); "busy" while a run works, "empty" with no queue. Session method `retryQueued` (`apps/server/src/session-methods.ts`); the web shows "Not sent" plus a Retry chip whenever messages are queued and the session is not working (`queued-chips.tsx`). A stop with messages still queued and no run after `STALL_CHECK_MS` reads idle (`session-turns.ts` `idleIfStalled`), so a deadline hit never leaves the session "working". Tests: `converse/after-failure.test.ts`, `queued-chips.test.tsx`, `session-turns.test.ts`.
- **Turns cut by a restart resume at boot (slice 8)** — `Harness.open` alone schedules nothing (only `resume()` and progress calls do), so a cut turn used to sit idle silently until something else woke the scheduler. `entity.ts` calls `converse.resume()` (`control.ts`, wraps `harness.resume()`) after every registry install, so resumed turns see the built-in tools; connector tools join as their servers connect. A turn cut `restartLimit` (5) times in a row ends instead (pi-durable 1.5: `pi.live.runFailure`, reported `task_interrupted`); `control.ts` keeps those reports (`interruptedRuns`, fed by `Harness.open`'s `onReport`) and Needs you lists the turn while its failure stands, with Retry (a `continue` submission, no new message). The list is in memory: it covers turns interrupted since this boot (test: `converse/parked.test.ts`). In the chat, a run this session did not start reads "working" while it runs (`session-turns.ts` `adoptedPhase`, applied on every view publication in `session.ts` `hydrate`). Test: `converse/resume.test.ts` (sqlite file, crash simulated by a second open without closing the first).
- **Turn deadlines (D4)** — `packages/mind/src/converse/deadlines.ts`, wired in `entity.ts`. Each model request must stream something (text, reasoning or a tool call) within the first-token deadline (default 60 s), and a run ends after the turn deadline (default 15 min). Per bot: `policies.firstTokenDeadlineSec` (10–1800) and `policies.turnDeadlineMin` (1–720), null = default. Bounds and the dialog's labels live once in `@spriessen/contracts` (`DEADLINE_FIELDS`, `deadlineProblem`): `profiles/update.ts` `validatePatch` refuses with the dialog's words ("First reply (seconds) must be a whole number from 10 to 1800. Leave it empty for the default."), and the Edit-bot dialog checks the same before sending and shows the problem under the field. A `beforeRequest` hook starts a per-conversation watcher (polls `liveOf` every second, stops when idle), so every path is covered, recovered runs included. Each request attempt (tool round or durable retry) gets its own first-token window; a retry's backoff sleep and deferred polls are not waits; a pending approval pauses both clocks. A hit aborts the run like Redirect (partial kept as interrupted, queued messages kept, never auto-sent, see D3; the session ends idle, not errored) and writes a `ultiv.turn-notice` entry the transcript shows as a note. Retries underneath: pi-durable retries a retryable model error 3 times (2/4/8 s backoff); the SDK itself is left at 0 retries and its own request timeout, so the deadline is the real bound. The abort is not a model error, so it is never retried.
- **Approval modes** — `policies.approvalMode` per profile (`manual` default | `jev` | `yolo`), set from the chat header's mode chip (Manual / Jev / YOLO; moving into YOLO always confirms and lists the floors, `lib/approval-mode.ts` `needsConfirm`), the Crew profile's Access tab, or the Edit-bot dialog. The floors (`isApprovalFloor` in `packages/mind/src/jev-gate.ts`: a credential's first use, an MCP connector's first use, connector changes, `secret_request`) always reach the owner, in every mode and whatever `policies.autoApprove` says. `yolo` approves everything else, the bash tool's beyond-VM targets (`host`, `node`) included — but never past the host-access switch (`entity-parts.ts` `wirePolicies`). `jev` runs `makeAdjudicator`: never decides floors or `JEV_NEVER_DECIDES` (the bash tool's beyond-VM targets); sends structurally complex calls back with a split note and unjustified destructive calls back with an explain-or-ask note (a third send-back becomes a card); otherwise Jev scores the call against the bot's description, the owner's latest message and the last 5 tool calls (redacted), approving at ≥0.8 (≥0.9 for a justified destructive call) and denying below 0.2, else the card. Each verdict is audited (kind `adjudication`) and shown as a line under the tool call; no answer within 8 s (`ADJUDICATE_TIMEOUT`) means the card. "Always allow" (`profiles.allowTool`) on a beyond-VM bash card saves only an EXACT entry, `bash@host:=<script>` or `bash@node:<id>:=<script>` (`exactEntry` / `exactScriptOf` in `auto-approve.ts`): it matches a call whose input is exactly `{ script }` (plus the resolved target) with the identical string — no globs, prefixes or other fields, scripts up to `MAX_EXACT_SCRIPT_CHARS` (2000). Bash is ONE tool with an optional `target` (`vm` default | `host` | `node`): bare `bash` grants and `bash:…` patterns match ONLY `vm` calls — a stored grant never widens because the tool merged — while `host`/`node` calls are exact-entry-only, never bare or pattern, never Jev-decided, and the host-access switch (`apps/server/src/host-switch.ts`) gates both, re-checked at approve/decide time. A saved node rule matches the next identical call by NAME (the autoApprove hook resolves the paired node through the registry before matching). Stored `bash_host:=` entries were migrated to `bash@host:=` (`packages/mind/src/migrate/shell-targets.ts`). `bash` with `background: true` is a BACKGROUND JOB (`packages/ext/src/plugins/bash-jobs.ts`; the tool's plumbing is in `bash-run.ts`): same approval, answers at once with a job id, the exec continues in-process (30 min cap, 3 per conversation, never moves the foreground cwd; a call that would reload a VM workspace a job is using is refused), and its end wakes the conversation with a `[job <id> finished] exit N: <first line>` input (steer, request id `bash-job:<id>`). The mind records running jobs in `ultiv.bash-jobs` (`packages/mind/src/act/bash-jobs.ts`); at boot each still on record wakes its conversation as `[job <id> lost]` (check its effects before re-running). Both clients draw these as job cards/lines (`@spriessen/present` system-text `job`). The cards read "Always allow this exact command on this computer" / "…on that node" (`alwaysAllowText` in `apps/web/src/lib/approval-text.ts`); the Access tab lists an entry by its script (`describeAllowEntry`) and removes it with a policies patch. `allowTool` refreshes the per-conversation profile copies, so a saved rule applies from the next call.
- **Image and file attachments** — the composer's + menu (`composer-attachments.tsx`) stages up to 8 files as chips (paste and drag-drop too), 10 MB each (`MAX_UPLOAD_BYTES`, the server 413s over it), photos over the image budget downscaled (`lib/image.ts`); upload happens at send time into the session's bot store. The server (`buildInputContent`) inlines images as content blocks only when the session's model accepts image input, reference lines otherwise; the composer warns on a text-only model. `artifact_read` hands viewable images to models as image blocks.
- **Checklist tool** — `checklist` (`packages/mind/src/checklist/`: rules in `checklist.ts`, tool + `ultiv.checklist` doc family keyed by conversation in `tools.ts`; parameter schema and caps in `@spriessen/contracts` `chat-tools.ts`, shared with the web card). A bot's visible plan for multi-step work in the chat it works in: `items` replaces the whole list, `update` changes items by number, at most 12 items of 120 chars, one `in_progress` at a time. It touches only its own conversation's list, so it is not gated; it rides the bot tools (allowlist universe, audited). `details` carries the list after the call (`listId` stays while a list is unfinished; a list after a finished one gets a new id). Web: `checklist-card.tsx` ("Tasks 2/4", a progress bar, ticked and struck-through done steps, the one in progress amber), shaped in `lib/chat-tool-views.ts`; `latestPlans` drops earlier calls of the same `listId` before grouping, so one card per plan sits at its latest update and changes in place (running and refused calls stay plain lines).
- **Graph tool** — `graph` (`packages/ext/src/plugins/graph.ts`, always installed): Mermaid text rendered to SVG with Pele (`pele`, MIT, zero dependencies, pinned exact in the catalog) ON THE SERVER, links and images off, source capped at `GRAPH_MAX_SOURCE` (20 000 chars, `@spriessen/contracts` `chat-tools.ts`). The model gets a one-line result, or Pele's error in words it can act on (syntax errors carry line and column; an unknown first line names the common types); the SVG never enters model context. `details` carries `{ type, width, height, title }`; the web draws the same source as a card. Not gated: it reads nothing and writes nothing. Web: `components/diagram.tsx` redraws from the call's `source` with `pele/lazy` (loaded on first use, measured with the app font) and inlines the SVG only after `lib/svg-sanitize.ts` (pure-string allowlist: drawing elements only, dropped with their content otherwise; no `on*`; links and `url()` only to `#ids`; no `javascript:`/`data:`/`@import`/`expression`); colours are the `--pele-*` variables in `components/diagram.css`, mapped to the tokens so light and dark follow without redrawing. The card has copy-source and a larger view (natural size, a bottom sheet on phones); a source the browser can't draw shows why plus the source, never a blank card. - **Mailbox deadline** — each bot-to-bot request expires after `MAILBOX_DEADLINE_MS` (default 15 min) and NACKs the sender.
- **PWA + Web Push** — web: `apps/web/public/` (`manifest.webmanifest`, `icons/`, `sw.js`, `offline.html`), `lib/push.ts` (SW registration, per-tab presence heartbeat, subscribe), `lib/push-support.ts`, the Notifications setting on `/settings` (`components/push-toggle.tsx`). The service worker caches ONLY `offline.html` + the icon at install; it never caches `/api`, `/chord`, `/hooks`, page HTML or any runtime response. Server: `apps/server/src/push/` — VAPID from `.env`, owner-scoped subscriptions in `PUSH_DIR` (default `<data>/push`, 0600), endpoints restricted to the browser push services (SSRF guard), a notifier that skips while any of the owner's tabs is visible, collapses the same tag for 30 s (plus the Topic header) and caps 6/min per owner, pruning 404/410 subscriptions. Pushes fire on: task done/failed (`tasks.listen`), approval waiting (`approvals.listen`), a webhook/cron/sensor turn settling with a reply (`deliverToSession(..., source)`), a bot-to-bot message timing out (`mailbox.onExpired`) — but never for a quiet check-in: a routine reply or routine task result of exactly `[nothing to report]` (`@spriessen/contracts` `quiet.ts`, docs/ROUTINES.md) sends nothing and renders as one dim line in both clients. Payloads carry the bot name and event kind only (no tool input, results or message text); a tap opens `/c/<sessionId>`. Push needs a secure origin: the HTTPS tailnet URL (or localhost); on iPhone only from a Home Screen install.
