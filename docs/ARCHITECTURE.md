# Architecture

Where everything lives, package by package. AGENTS.md has the rules for
working in the repo; this file is the map. Feature-level contracts are in
[FEATURES.md](FEATURES.md), the web client in [WEB.md](WEB.md), models and
Jev in [PROVIDERS.md](PROVIDERS.md).

Paths written `<data>/…` live in the data folder: `~/.spriessen/data` (`SPRIESSEN_DATA_DIR` moves it; an install from before the home keeps the old relative `var/…` until `spriessen data move`), resolved through `dataPath` in `@spriessen/core`.

## Shape

Effect-first, AI-native web app as a pnpm-workspace monorepo. The core is
three packages: `@spriessen/core` (the kernel), `@spriessen/ext` (the
extension platform) and `@spriessen/mind` (the entity substrate: one
runtime, one entity per profile; a fresh install seeds no profile and the
first bot created becomes the main bot). `apps/server` (Node 26) is a thin
chord host over the mind; `apps/web` is the thin client over replicated
chord state and REST; `apps/cli` is the terminal client on the same
surfaces; `packages/contracts` holds the JSON Schema contracts (pi-schema builders) all of them
share.

## Packages

### `@spriessen/core`

The kernel, no domain knowledge. Deps: `effect` only.

- `home.ts` (the ONE home, `$SPRIESSEN_HOME` or `~/.spriessen`: `data/` for everything the server keeps — `dataDir()`/`dataPath()` are the default of every data env key (`HARNESS_DB`, `VAULT_DIR`, `ARTIFACTS_DIR`, …; `SPRIESSEN_DATA_DIR` moves the folder); `sources/`, `.env`, `config/`, `logs/` for the CLI install. An install whose server cwd still has `var/harness.sqlite` while the home has no data keeps the EXACT old relative `var/…` strings (bots' microVM names hash the path as written) and warns once; `spriessen data move` migrates. Never hardcode `var/`: use `dataPath`; tests point the home at scratch through `packages/mind/test-env.ts`)
- `errors.ts` (shared tagged-error taxonomy: `NotFound`, `InvalidInput`, `Duplicate`, `Unavailable`, `AuthMissing`, `External`) and `runtime.ts` (`openRuntime(layer, key)` — builds a fully-provided Layer into a live service under a caller-owned scope; the door promise-land code enters through).

### `@spriessen/ext`

The extension platform.

- `tool.ts` (pi-durable-shaped `Tool` + `gated` flag; pi-durable is a TYPE-ONLY dep here)
- `connector.ts` (auth specs — `none | env | vault` — + JSON-Schema-typed actions + `invoke`: validate → authenticate → perform; `vault` auth redeems a sealed item through an injected `AuthSource`, so credentials never cross a model-facing surface)
- `plugin.ts` (`definePlugin` + capability union `tool | connector | section` — new kinds extend the union)
- `registry.ts` (the `Registry` service: tools/sections/connector resolution; duplicate identities fail at build time)
- `vault.ts` (the credential vault: per-item AES-256-GCM DEK under a `VAULT_KEY`-derived KEK, masked metadata, `secret` vs `reference` access classes, contacts readable, single-use 60s grants for future executors, export/import of sealed forms)
- `plugins/http.ts` (reference HTTP egress connector + `vaultedHttpConnector` proving vault-backed bearer auth)
- `plugins/tinyfish.ts` (TinyFish live-web egress: `tinyfish` connector + the `web_search`/`web_fetch` tools, env `TINYFISH_API_KEY` — the plugin installs only when the key is present)
- `plugins/vault.ts` (`vault_list` masked metadata + `vault_contacts` — NO tool returns secret bytes, by construction; also the `ScopeHolder` the mind sets so ext plugins partition per profile)
- `plugins/artifacts.ts` (the artifact store: blob+JSON-sidecar files under `ARTIFACTS_DIR` (default `<data>/artifacts`), partitioned `{owner}/{profile}` when the scope holder is wired; the server's REST serves it) + `plugins/artifact-tools.ts` (`artifact_write` / `artifact_read` / `artifact_list` — writes are NOT gated, `artifact_delete` is). ONE TREE PER BOT: a bot's files are its `DurableFs` tree (`fs/durable-fs.ts`, path index in the reserved `vfs-index` pair, sidecars carry `path`/`updatedAt`, every change re-reads the index first so no writer drops another's file); every writer that is not bash goes through `fs/tree.ts` `putFile` — `artifact_write` by path (a taken path is REPLACED in place: same id, so old cards show the new content), uploads to `uploads/`, browser screenshots to `screenshots/`, grants (`grantInto`) to `received/` (those three take a free `name (2).ext`) — and bumps the workspace epoch so the VM reloads. Overwrites keep the old bytes as hidden versions (`fs/versions.ts`: own blob+sidecar with `versionOf`, never listed, still served by id; last `MAX_VERSIONS` 10, none under `SKIP_DIRS` or over 2 MB; REST `GET /api/artifacts/:id/versions`, `POST …/versions/:vid/restore`, the preview's Earlier versions menu `components/file-versions.tsx`); deletes go through `removeFile` (every path, versions, bytes). Files from before the tree (loose sidecars) are adopted at server boot by `fs/adopt.ts` (same-name text files → one file + versions, others at free names; the legacy root stays loose)
- `plugins/files.ts` (`file_read` / `file_search` open, `file_edit` / `file_delete` gated: path tools over the bot's own durable tree, refusing anything outside it; docs/SECURITY.md; plus `extract_document_text` for PDF/.docx through `docs/extract.ts`)
- `plugins/code-intel.ts` + `codeintel/{parser,symbols}.ts` (web-tree-sitter over the bot's own tree: `code_outline`/`code_nav` open tools + `file_find`/file_edit syntax notes in files.ts; TypeScript/TSX/JavaScript/Python; WASM loads lazily — importing ext never loads the runtime; docs/BOT-FILES.md). Lifecycle is Effect layering, not plugin callbacks.

### `@spriessen/mind`

The entity substrate: **one runtime, one entity per profile** (RFC 0001; no profile is seeded — the first bot created claims main). The faculties below are the core; the newer ones (projects, evals, skills, checklist, routine trials, the chats/tasks split, task queues) are written up in [FEATURES.md](FEATURES.md).

Faculties:

- `converse` (pi-durable harness: `root`/`ensure(key, agent?)`/`submit`/`settle`/`turn`/`configure`/`agentOf` + `docs` for app-level session-scope documents + `projectTranscript`/`usageOf` — the projection and spend accounting every surface renders through)
- `decide` (Jev: `yesNo`/`pick`/`rate`/`ask`, independent of any conversation)
- `act` (tools assembled from the Registry; `gated` tools wrapped by the approval broker — gates ACTS, never ASKS; every execution rides `withAudit`, which stamps the acting conversation's profile)
- `generate` (one-shot structured completion for app features — titles, extraction; prompt-only JSON against a JSON Schema (pi-schema) with one repair retry, NEVER `response_format`; `mind.generate.complete/extract`)
- `tasks` (background sub-agent turns in their own durable conversations — `spawn`/`get`/`list` over the `ultiv.tasks` doc; when a task settles it WAKES the conversation that spawned it with the outcome, so parents end their turn instead of polling; task conversations are ADOPTED under the spawner's bot scope (kind "task"), so a task messages/artifacts/remembers AS its bot; on boot still-running tasks are RESUMED with a continuation input — restarts never reap work; queue, limits, continuation and the chats/tasks split: [FEATURES.md](FEATURES.md))
- `profiles` (`profiles/profiles.ts` — the `ultiv.profiles` doc + session registry v3 with profile/kind/participants; Bot Mode main chats (reset rotates the id), per-pair DM threads, the conversation→profile index persona/audit/artifact scoping all read, per-profile agents (model default + tool allowlist + the sandbox exclusion via `converse.ensure`'s agent override — `policies.sandbox: false` removes the `bash` tool from the bot's conversations; a tool-affecting PATCH re-applies the agent to every existing conversation through `converse.configure`'s `tools` selection; a PATCH that changes the tools, sandbox, host access or approval mode also leaves an `[access changed]` note with the bot's RUNNING work only (running tasks, chats with a turn in flight; `profiles/access-notice.ts`, no turn, no push)), `profiles/rooms.ts` — contextual rooms as tunnel records (no seat conversations — endpoints are the participants' own threads); the settings doc holds the ONE main bot (`mainOf`/`setMain`, REST `/api/main`); creation seeds an onboarding first turn from name/description/persona unless `onboard: false`; `ensureMain` is single-flight) and `profiles/section.ts`'s dynamic identity section: profile persona + a COMPACT sibling roster (name, id, ≤80-char role, at most 20 lines; details via the read-only `bots_list`/`bot_info` tools in `profiles/bots-tools.ts`, which follow the allowlist and never expose memory, files, vault or chats), or the substrate baseline for unmapped conversations)
- `mailbox` (`mailbox/mailbox.ts` — inter-bot messaging in CONTEXTUAL ROOMS (see `profiles/rooms.ts`): ROOMS ARE TOPICAL — a pair may hold many rooms by topic, and conversation shape comes from topic + freshness, not a send counter (the per-exchange cap is gone); async only: admission is the contract, lineage hop caps (3), cycle refusal, per-pair rate (10/h), the 24h stale-room rollover (`ROOM_STALE_MS`: a send into a room quiet past it opens a fresh room, topic stamped `· YYYY-MM-DD` by `rolloverTopic`, the old room stays readable; `currentRoomOf` resolves the most recently active room of the topic's LINEAGE (`baseTopic`), so later sends under the base topic continue in the fresh room instead of rolling over again; the stamp always survives the 200-char cap), the Jev-gated, fail-open off-topic refusal for established rooms (≥ 3 envelopes; `topic.test.ts`), per-profile daily budgets, lane caps so bot traffic never starves the owner, bounded retries → dead-letter + escalation. THE ROOM IS A TUNNEL (no seat conversations): delivery lands on the recipient's MAIN thread (thinking happens there, in the open); each send records its ORIGIN conversation (main or the session it was sent from) and replies/NACKs signal THAT thread — a session-origin exchange runs session ↔ counterpart-main. Wakes carry a finish SIGNAL + room id, never a transcript copy; the `room` tool reads a room's full envelope transcript for its PARTICIPANTS only (another bot reads it as missing); topics normalize once (`normalizeTopic`: trim, 200 chars) on send, on read and in `rooms.ensure`, which finds-or-inserts in one commit; `mailbox.listen` hears every committed write; stored delivery errors are `ownerErrorText` sentences (scrubbed again on read). Initiation is OPEN by default (`canInitiate: ["*"]` — explicit list restricts, `[]` locks, cron sends always pass); `deliverExternal` enforces the stricter external trust class — no artifact grants, never autonomous)
- `memory` (`memory/` — v3, full contract in `docs/MEMORY.md`: tiers in doc families `ultiv.mem.core/facts/graph/episodes/proposals` (archived facts stay in facts; `ultiv.mem.archive` is unused); facts carry kind/importance/trust/basis/validity/supersede history and why a version retired (`changed|corrected|ended`) — nothing deleted but the owner's Purge; every model-facing line leads with a `#handle` (the id's first 8 chars) that every id-taking tool resolves (`handles.ts`) — the model never sees structured output; `memory_update` (change / correct / end / confirm, `tools-update.ts` over `lifecycle.ts` and the guarded write path in `tools-write.ts`) for bots, `POST /api/memory/v2/facts/:id/update` for the owner; tool dates are days (`dates.ts`); bilingual EN/ID ranked recall (RRF over FTS5 BM25 words, entities, graph, trigram letters, an optional local-embedding meaning leg and an importance×recency prior; `asOf` answers what held then) in `recall.ts`/`text.ts`/`lexicon.ts`; recall BEFORE EACH TURN through the `recalled_memories` prompt section (`prefetch.ts`: a fact passes on ≥30% rarity-weighted coverage of the message's known words, a distinctive single word, or a named entity; ≤5 facts, ~300 tokens; not repeated within 6 inputs; `MEMORY_PREFETCH=off`; the same stores `memory_recall` reads, team store included; each line carries a source cue and `memory_history` expands it into the evidence — chat kind, day, the saved note — `evidence.ts`); the write guard (`guard.ts`) stamps origin off the input's bracket prefix and turn taint, refuses secrets and non-owner instructions; writes consolidate (dedupe → supersede on normalized functional predicates (`predicates.ts`) → Jev/generate → add) with the decision taken OUTSIDE `docs.commit` (one lock for every durable write) and re-decided by rules inside it if the store moved (`consolidate.ts`); core memory (owner 120w keeper-gated, bot 80w) rides its own `memory_core` prompt section (`profiles/section.ts`) and tool; the weekly tidy (Sundays 09:00 WIB, `apps/server/src/memory-tidy.ts`) only PROPOSES — contradictions (`conflicts.ts`; the owner keeps one side, `memory/proposals.ts`), stale, soft-limit archives, merges, secrets — nothing changes without the owner's accept; `SPRIESSEN_MEMORY_V2=off` is a fallback to the v1 seam, not a full rollback; the v1 mirror and migration are gone (2026-10-28, nothing left to migrate))
- `search` (`search/` — the derived SQLite FTS5 sidecar, `SEARCH_DB` default `<data>/search.sqlite`, in memory on test storage, rebuilt on a schema bump: fact rows synced per store by signature before each recall, conversation messages indexed per bot by entry cursor before each search; `unicode61` terms from our own analysis + `trigram` raw text + optional float32 vectors (`MEMORY_EMBEDDINGS`: `ollama`, `<provider>/<model>` through the catalog provider's own endpoint and key (`providers/embedding-endpoint.ts`, e.g. `kenari/bge-m3`), or `openai-compatible` with `EMBEDDING_URL`; `search/embedders.ts`; a remote endpoint is never sent tool results; the cutoff adapts to the model's baseline; status in Settings › Server via `mind.meaning()`); purges drop rows at once)
- `history` (`history/` — `history_search`: ranked full-text search over ONE bot's chats (rows carry owner + profile, every query filters on both), bilingual, typo-tolerant, time phrases narrow the window (`search/when.ts`); `GET /api/history/search` and Past chats' Messages section for the owner; a substring scan only when the sidecar is unavailable)
- `audit` (append-only JSONL of tool calls + approval/mailbox/escalation events, `AUDIT_LOG`, default `<data>/audit.jsonl`, entries carry the acting profile)

Wiring:

- Act extras: codemode (`act/codemode.ts`), the task tools (`act/task-tools.ts`), the message + room tools (`mailbox/tools.ts`), and the memory tools (`memory/tools.ts`).
- MCP connectors (`mcp/` here over `@spriessen/ext` `mcp/`: HTTP/SSE/stdio, config under `MCP_DIR`, OAuth via `MCP_OAUTH_CALLBACK_URL`) install live per server; bots manage them with `connector_*` tools whose changes are NEVER auto-approved, and keys arrive only by vault item or the `secret_request` secure field (`secrets/`, REST `POST /api/secrets/:callId`) — never as tool arguments, never in model context, transcripts, audit or logs.
- The act + codemode + task + profiles + mailbox + memory extensions install into a SHARED pi-durable registry (`converse/pi-registry.ts`) from `entity.ts` — late installs are legal, which breaks the tasks→converse layer cycle.
- `entity.ts` composes the services into `Mind` (`openMind(options)` is the promise-land entry; `mindLayer(options)` Effect-native) and wires the scope holder the ext plugins read.
- Owner rule enforced here: `turn` (submit → wait → commit) is the only path an input reaches a model — `generate` is the ONE sanctioned non-conversational exception, and it lives inside the mind.
- Model concurrency is bounded process-wide by the Gate (`providers/gate.ts`, `MODEL_MAX_CONCURRENCY`, default 4): the slot wraps stream CONSUMPTION (result()/iteration) — never wrap the stream call itself in a Promise, the harness iterates it synchronously (that faulted every live turn once); the gated methods are shadowed onto the instance so pi-ai's complete/completeSimple pass through too. The gate has two LANES (`providers/lanes.ts`): a `beforeRequest` hook marks each request by its conversation — task conversations and test replays are `background`, everything else (and anything unmarked: titles, compaction) is `owner` — through the run's abort signal and the `ProviderDoc` session id the request's options carry; a waiting owner request is admitted before any waiting background one, and background work holds at most `limit - 1` slots, so the owner's chats always have one while tasks crowd in (the total never exceeds the limit).

`docs/design/dsh-superagent.md` maps every dsh-superagent concept onto
Spriessen (what existed, what was built from it, what does not apply and
why).

### `@spriessen/about`

The app's self-knowledge as first-party Agent Skills (`skills/`, one folder per SKILL.md); the mind ships them as the read-only `builtin` tier of every bot's skill list. `src/drift.test.ts` keeps the prose honest: every tool it names in backticks must be defined by a package, every nav label (`apps/web/src/lib/nav.ts`) must appear in `references/surfaces.md`, and dropped descriptions (seat conversations, owners posting in bot talks, the old place names) fail the build. Change the app, update the skill in the same commit.

### `@spriessen/present`

The owner-facing words BOTH clients share: the tool-call lens (`tool-text.ts` `presentationOf` + the per-area views), approval-card words (`approval-text.ts`), file kinds, durations. Pure TS over contracts, imported by subpath (`@spriessen/present/tool-text`); `apps/web/src/lib/<name>.ts` keeps one-line re-exports so web imports never changed.

### `@spriessen/contracts`

Chord contracts (JSON Schema, built with `@earendil-works/pi-schema`). All `remote()`/`local()` definitions live here; both apps import `@spriessen/contracts` (`workspace:*`). `Session` is v17 (usage/model/effort state + `configure` + `input` attachments; input transcript entries carry `AttachmentRef` chips, and `ModelInfo` carries the model's input modalities). The session registry, model catalog, tasks, artifacts, webhooks, cron jobs and the audit tail are NOT chord objects — they are plain REST on the server's HTTP handler with payload schemas in contracts, because chord 1.4.0's replicated-object wire desyncs on attach (see Pitfalls).

## Apps

### `apps/server`

- `apps/server/src/main.ts` — `buildStack()` (`webDist` serves the web build in-process, `static.ts`; `start.ts` `startServer` takes the data-folder lock `data-lock.ts` — one server per `var/`, a live holder waited for then refused by pid — builds and listens; `index.ts` exports `serve()` for the CLI): `openMind({ plugins: [httpPlugin] })` (TinyFish egress auto-installs inside the mind when its key is present; the artifacts plugin always) → cron scheduler boot → chord `createHost` + `acceptWebSockets` (`ws`) + REST; `close()` stops the scheduler, tears down links, then the mind's scope (harness finalizers). Dev runs unbundled (Node strips TS types).
- `apps/server/src/identity.ts` — the principal seam: every request and socket authenticates through the sign-in session (`auth/guard.ts`: passcode or passkey, an HttpOnly SameSite=Strict cookie; no session, no access — loopback included) and runs as THE one owner account (`OWNER_ID`); `ownerOf`/`sessionKey` partition the registry and conversation keys. Header-claimed identities are not read. A real IdP replaces ONLY this module and `auth/`.
- `apps/server/src/session.ts` / `sessions.ts` — the app-facing boundary: `session.ts` is the chord Session object (replay, approvals + their audit records, configure, `input` with artifact attachments); `sessions.ts` is the REST-backed registry (owner-scoped list/create/remove + `touchSession`, which titles sessions through the generate faculty, falling back to truncation on any failure).
- `apps/server/src/rest.ts` — the REST dispatcher (routes live in `rest/`): sessions (profile-scoped), models, tasks, artifacts (per-profile dirs, raw bytes on GET with owner check), webhooks (+ `POST /hooks/:id?token=…` ingress), cron (tz-aware per profile, auto-disable on 3 consecutive failures), profiles/bots (CRUD, Bot Mode ensure/reset, archive, purge cascade — which also DESTROYS the bot's microsandbox VM (`destroySandbox`/`sandboxNameOf` from `@spriessen/ext`, 8 s bounded, never fails the purge) — export/import bundles, set-main `/main`, `GET /api/main`; the main bot and last bot are not removable), rooms (`GET /api/rooms` (+`?bot=`), `GET /api/rooms/:id` and `/by-envelope/:id` → the tunnel transcript as one speaker-labelled timeline, lines carry `speakerId` — never sessions; rooms are bot-to-bot only and READ-ONLY to humans: no say, no human send-as-bot, no cancel route), mailbox (read-only: list, dead-letter list; `mind.mailbox.listen` → the live `mailbox` signal), vault (human-only secret entry, masked responses), approvals (the cross-profile inbox + REST decide), vault bindings (`GET /api/vault/bindings`, `PUT|DELETE /api/vault/:id/binding`), push (`/api/push/config|subscribe|unsubscribe|presence|test`), memory, memory v2 (`rest/memory-v2.ts`: `GET /api/memory/v2` facts/core/proposals + the bot's chats by conversation id for "Learned in …", proposal accept/reject in one commit through `decideProposal` (a conflict's accept names the fact kept, `{ keep }`; a decided proposal is 409), core CRUD, `POST /api/memory/tidy/run`, `POST /api/memory/purge` — irreversible; `rest/memory-facts.ts` the owner's change/correct/end/confirm), conversation search (`rest/history.ts`: `GET /api/history/search`, one bot or each of the owner's bots, grouped), audit tail (`?profile=`/`conversation`/`kind` filters through `audit.find`, which widens its window until it has enough, so a quiet bot's events are found past busier bots'), `rest/needs-you.ts` (`GET /api/needs-you`: open tidy proposals per bot, routine escalations from the last 7 days, and each pending approval's chat; read-only), `rest/server-check.ts` (`GET /api/server/check`: which keys are set — names only, NEVER values — models, microVM support, listen scope); owner scoping rides the signed-in session (`OWNER_ID`). Mind-service calls here go through `Effect.runPromise` — they are Effects, not Promises.
- `apps/server/src/deliver.ts` / `webhooks.ts` / `cron.ts` / `sensors.ts` — the trigger path: webhooks, cron and calendar sensors deliver into sessions through `deliverToSession` — admission is the contract; the turn settles in the background, and a failed TURN is never a failed delivery. Routine wakes STEER a busy turn (`whenBusy: "steer"`); sensors queue as follow-ups. Cron jobs live in the `ultiv.cronjobs` doc; the scheduler re-arms from it on refresh and on boot. A recurring job in TRIAL mode (`trial: true`) runs each fire through `mind.trials.runCron` (`packages/mind/src/routines/trial.ts`: the same input and model as the live fire, in a `trial:<job>:<run>` conversation the evals dry-run guard holds, so no tool runs) and keeps what it would have done on the job (`trials`, last 3); Routines has Try now (`POST /api/cron/:id/try`), Go live and Pause/Resume (`PATCH /api/cron/:id`). Watches and webhooks take the same `trial` mode (`mind.trials.run`, `PATCH /api/sensors/:id`, `PATCH /api/webhooks/:id`): a watch's event or a webhook's allowed payload runs as a trial instead of waking the bot, receipted `trial`. Cron and webhook fires both write WRITE-AHEAD receipts into the `ultiv.routine-events` doc (the routines faculty in the mind — see `docs/ROUTINES.md` for the whole contract); webhook ingress validates size/rate/schema BEFORE the ack (ack body carries the correlation `eventId`); a webhook may route each outside THREAD to its own chat (`threadKey`/`threadTitle` dotted paths, `packages/mind/src/webhooks/route.ts` + `threads.ts`, thread→chat map on the webhook) and gate who may start work (`senders {path, allow}`: others only add a context-only note to an existing thread chat, else receipted `ignored`); deliveries debounce per session (`WEBHOOK_DEBOUNCE_MS`, default 2.5s), retry 3x, then dead-letter with an audit escalation. The sensor loop polls per kind — the calendar ICS feed, per-sensor RSS urls, and watch urls (edge-triggered fingerprints) — dedups by the source's natural key (or fingerprint transition), and wakes as a follow-up.

### `apps/web`

React 19 + TanStack Router + shadcn on Base UI + Tailwind 4 (no Effect in the client); `vite.config.ts` imports `defineConfig` from `"vite-plus"` (vp rewrites this on `vp migrate`) and loads `tanstackRouter` → `tailwindcss` → `react` plugins. Details: [WEB.md](WEB.md).

- Root `vite.config.ts` — workspace-level vp config; only sets oxfmt `ignorePatterns` (the generated route tree).

### `apps/cli`

The `spriessen` command ([CLI.md](CLI.md)). A terminal client on the SAME surfaces as the web: REST + the chord `Session` over `ws` (`client/session.ts`: the link attaches BEFORE the socket opens — `ws` can emit the server's hello with `open`, and a missed hello makes chord refuse the first ack) + the `/push` live signals. EVERY command is one row of `src/table.ts` (summary, usage, flags, booleans, subcommands, lazy `run`): dispatch, `--help`/`help <cmd>` (`help.ts`), the unknown-flag refusal and "did you mean", and `completion bash|zsh|fish` (`completion.ts`) all read it — a new command or flag is added THERE or it is refused. Naming is one rule (`commands/context.ts` `matchBot`/`matchId`, shared with the TUI): a bot by id, name or unique name prefix; chats/tasks/cards by id or a ≥4-char unique prefix (`render/out.ts` `shortId`). A client command that finds you signed out in a terminal asks for the passcode in place and retries (`main.ts`, `auth.ts` `signInHere`). Sign-in is the web's own passcode route; the session cookie lives 0600 in `~/.spriessen/config`. The TUI (`tui/`, OpenTUI React 0.8.2 on Node's FFI; opened through `tui-door.ts`) shows the chat, approval cards (a/d/A), Needs you, the crew, and the pickers (`pickers.tsx`: bots ctrl-k, chats ctrl-o, models) and the help panel (`help-overlay.tsx`); machinery inputs render as one dim line through `@spriessen/present/system-line` and reactions as "X reacted 👍"; slash commands are one table in `tui/slash.ts` (`SLASH_COMMANDS`: hints under the composer, tab completion, help) run by `use-slash.ts` (/help /new /chats /bot /model /edit /branch /copy /retry /stop /test /open, `//` escapes); the composer clears its input imperatively on submit (a paste-and-enter can outrun the draft state). Line commands: `ask` (live in a terminal through `render/follow.ts`, the reply's words only into a pipe; `--new`, `--chat`, stdin with `-`), `bots [new|main]`, `chats [show|new]`, `search`, `memory`, `routines`, `tasks [show|stop]`, `projects`, `models [default]`, `tests [run]` (exit 1 when any test fails), `needs`, `approve [--all]`/`deny` (bulk approve skips cards that are asked every time and beyond-VM scripts), `doctor` (the first-run path, exit 1 while something is wrong), `open`, `completion`, `version`. `serve` runs `@spriessen/server`'s `serve()` from the server's folder with the web build in-process (NOTE: with no data in the home and an old `apps/server/var/harness.sqlite` present it uses that folder — pass `--data` for a scratch server); `daemon` installs it (or `node`) as a systemd `--user` unit / launchd agent; `node` runs and pairs this machine.

### `apps/agent`

The node agent (bash's `node` target on the owner's other machines; docs/SECURITY.md "Paired nodes"): dials OUT to `/agent` with its pairing token as a Bearer header (`?token=` still read for older agents), reads the token from a 0600 file (`--token-file`), runs each script in its own process group (`run-script.ts`: answers when bash exits, kills the whole group on timeout or `cancel`, scripts never inherit `SPRIESSEN_NODE_*`, answers scrubbed of the token), takes live `roots` frames, redials on missing pongs and stops on a refused token (close 4001). A library (`src/index.ts`) the CLI's `spriessen node` runs.
